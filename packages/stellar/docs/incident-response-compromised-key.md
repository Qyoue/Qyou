# Incident Response Runbook: Compromised Stellar Key

## Overview

This runbook defines the protocol for responding to a leaked, compromised, or suspected-compromised Stellar key (distribution signing key, issuing account key, or contract admin key).

- **Classification**: `SEV-1 (Critical Security Incident)`
- **SLA**: Initial containment within **5 minutes** of detection.
- **Incident Commander (IC)**: On-duty Security Lead / Principal Engineer.

---

## Response Team Roles

| Role | Responsibility |
| :--- | :--- |
| **Incident Commander (IC)** | Coordinates response, authorizes signer rotation, signs off on resumption. |
| **Stellar Tech Lead** | Executes kill switch, signs multi-sig key rotation transactions, inspects Horizon ledger. |
| **Comms Lead** | Prepares user-facing notices, coordinates status page updates and partner communication. |
| **Infrastructure Lead** | Audits AWS Secrets Manager / KMS, revokes IAM credentials, inspects server access logs. |

---

## Incident Response Workflow

```
[Detection / Alert] 
         │
         ▼
[Step 1: Emergency Kill Switch Activation] ──> Distributions Halted (< 1 min)
         │
         ▼
[Step 2: Signer Rotation via Multi-Sig]    ──> Compromised Key Weight = 0 (< 10 min)
         │
         ▼
[Step 3: Forensic Horizon Ledger Audit]    ──> Identify Drained Funds / Rogue Txs
         │
         ▼
[Step 4: Custodial Fund Sweep (If Needed)] ──> Sweep Pool to Cold Multisig Vault
         │
         ▼
[Step 5: User & Public Communication]      ──> Transparent Disclosure & Status Page
         │
         ▼
[Step 6: Resumption & Verification]        ──> Resumption Pre-flight Checklist & Kill Switch Reset
         │
         ▼
[Step 7: Blameless Post-Mortem]            ──> RCA, Action Items & Security Hardening
```

## Step 1: Emergency Distribution Halt (Kill Switch)

The moment a key leak is suspected, immediately trip the emergency distribution kill switch to freeze all outgoing payments. This does **not** require a redeployment.

### 1.1 Via CLI / Node REPL
```bash
node -e "
  const { DistributionKillSwitch } = require('@qyou/stellar');
  DistributionKillSwitch.getInstance().haltSync(
    'CRITICAL: Suspected signer key compromise. Halting distributions.',
    'IncidentCommander'
  );
"
```

### 1.2 Via API Endpoint (if configured)
```bash
curl -X POST https://api.qyou.app/api/admin/stellar/kill-switch/halt \
  -H "Authorization: Bearer $EMERGENCY_OPS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"reason": "Suspected signer key compromise", "haltedBy": "IncidentCommander"}'
```

*Verification*: Verify `DistributionKillSwitch.getInstance().isHalted() === true`. Any attempted call to `IncentiveService.reward()` will throw `KillSwitchActiveError`.

## Step 2: Signer Rotation via Multi-Sig Quorum

Under the Qyou 2-of-3 multi-sig architecture (`MultiSigService`), key compromise can be contained by using the remaining 2 non-compromised signers to revoke the compromised key and add a fresh replacement signer.

### 2.1 Generate Replacement Signer
Generate a new keypair in an isolated, secure environment (Hardware Security Module or offline machine):
```bash
node -e "
  const { Keypair } = require('@stellar/stellar-sdk');
  const pair = Keypair.random();
  console.log('Public Key:', pair.publicKey());
  console.log('Secret Seed:', pair.secret());
"
```
Store the secret key in AWS Secrets Manager / Vault under `STELLAR_SIGNER_KEY_NEW`.

### 2.2 Submit Signer Rotation Transaction
Construct and sign a transaction that:
1. Adds the new replacement signer with `weight: 1`.
2. Sets the compromised signer key weight to `0` (revoked).
3. Verifies thresholds remain intact (Low: 1, Med: 2, High: 3).

```typescript
import { MultiSigService } from '@qyou/stellar';

// 1. Propose rotation transaction
const rotationTx = await multiSigService.createSignerRotationTx({
  accountId: DISTRIBUTION_ACCOUNT_ID,
  revokedSignerKey: COMPROMISED_PUBLIC_KEY,
  newSignerKey: NEW_PUBLIC_KEY,
  newSignerWeight: 1,
});

// 2. Collect signatures from the 2 non-compromised cosigners
rotationTx.sign(CosignerOneKeypair);
rotationTx.sign(CosignerTwoKeypair);

// 3. Submit to Stellar Horizon
const result = await server.submitTransaction(rotationTx);
console.log('Signer rotated successfully. TxHash:', result.hash);
```

### 2.3 Verify On-Chain Account Signers
Inspect the distribution account on StellarExpert or Horizon:
```bash
curl https://horizon.stellar.org/accounts/$DISTRIBUTION_ACCOUNT_ID | jq .signers
```
Confirm the compromised key is no longer listed or has `weight: 0`.

## Step 3: Forensic Ledger Audit & Drain Detection

1. Check alerts generated by `AccountTransactionWatcher` (`getAlerts()`):
   - Review any unexpected outgoing transactions emitted during the leak window.
2. Query Horizon for all payments from the distribution account over the last 48 hours:
   ```bash
   curl "https://horizon.stellar.org/accounts/$DISTRIBUTION_ACCOUNT_ID/payments?order=desc&limit=100" | jq .
   ```
3. Reconcile on-chain transactions against internal database records using `EventReconciler`:
   ```bash
   npm run reconcile:ledger -- --account $DISTRIBUTION_ACCOUNT_ID
   ```
4. Calculate net unauthorized loss (if any).

---

## Step 4: Custodial Fund Sweep (Master Key Compromise)

If the compromised key is the root master key of the distribution account and thresholds were not locked:
1. Immediately sweep all remaining pool balances to the cold multi-sig vault:
   ```typescript
   // Drain remaining native XLM and assets to secure cold vault
   await client.emergencyWithdraw({
     destination: COLD_VAULT_ADDRESS,
     amount: remainingBalance - reserveBuffer,
   });
   ```
2. Deprecate the compromised distribution account permanently.
3. Deploy or fund a new distribution account.

## Step 5: Stakeholder & Affected User Notification

### 5.1 Communication Principles
- **Transparency**: Acknowledge the event promptly.
- **Scope Distinction**: Emphasize that user personal non-custodial wallets are untouched and only the queue incentive distribution account was affected.
- **User Guarantee**: Any legitimate pending rewards queued during the incident will be honored and distributed once the incident is resolved.

### 5.2 Notification Template (Status Page & In-App Notice)
```markdown
**Stellar Incentive Pool Maintenance & Security Update**
[Date/Time UTC]

Our automated security monitoring system detected unauthorized access to one of our
automated distribution signing keys.

- **Status**: The issue was immediately contained using our emergency circuit breaker.
- **User Wallets**: User personal non-custodial wallets are not affected and remain secure.
- **Incentive Distributions**: Queue completion rewards are temporarily paused while we
  complete our signer rotation and integrity verification.
- **Pending Rewards**: All eligible rewards earned during this window are queued safely
  in our database and will be processed once distributions resume.
```

## Step 6: Safe Resumption Protocol

Before lifting the kill switch, the IC and Stellar Tech Lead must verify the following checklist:

- [ ] Compromised signer weight is verified `0` on Horizon.
- [ ] New signer key is loaded in Secrets Manager and verified operational.
- [ ] All servers / pods have loaded updated secrets without plaintext exposure in logs.
- [ ] Automated transaction watcher (`AccountTransactionWatcher`) is active and healthy.
- [ ] Test distribution executed successfully on Testnet / staging.
- [ ] A small canary distribution (e.g. 0.00001 XLM) succeeds on Mainnet without alerts.
- [ ] Resumption signed off by Incident Commander.

### Deactivate Kill Switch
```bash
node -e "
  const { DistributionKillSwitch } = require('@qyou/stellar');
  DistributionKillSwitch.getInstance().resumeSync('IncidentCommander');
"
```

---

## Step 7: Blameless Post-Mortem & Remediation

Hold a blameless post-mortem meeting within 48 hours of resolution. Document:

1. **Incident Timeline**: Minute-by-minute timeline from key exposure to resolution.
2. **Root Cause Analysis (5 Whys)**: How did the secret key leak (e.g., CI log, developer machine, repository commit, dependency supply chain)?
3. **Detection Speed**: Time to detect, time to halt, time to rotate signers.
4. **Action Items & Preventative Measures**:
   - Automated secret scanners in git pre-commit and CI.
   - Restricting IAM permissions on Secrets Manager.
   - Enforcing HSM/hardware-backed cosigners.
   - Updating the dependency security policy and crypto scanning schedules.
